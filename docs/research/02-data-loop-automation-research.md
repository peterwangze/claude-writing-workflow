## 1. 调研背景与方法

### 1.1 问题定义

Claude Writing Workflow Plugin 的数据监控 SKILL（`data-monitoring`）当前所有平台运营数据（完读率、追读率、收藏数、阅读人数、收益等）**完全依赖作者手动输入**。作者需要每天登录各平台作家后台，逐项查看数据并复制到数据监控模板中。这是整个写作工作流中摩擦最大的环节。

### 1.2 调研目标

1. 摸底四平台（番茄小说、起点中文网/阅文系、七猫小说、晋江文学城）的数据获取/导出能力
2. 评估三种接入方案（完全手动 vs CSV 导入 vs API 接入）的阶梯式增量价值
3. 设计 CSV 导入方案（含 Schema、验证规则、错误处理）
4. 给出务实的实施路径建议

### 1.3 调研方法

| 方法 | 说明 |
|------|------|
| 官方文档调研 | 各平台帮助中心、开放平台文档、公告 |
| 社区经验挖掘 | 知乎、龙的天空、CSDN、GitHub 等社区中作者分享的实际使用体验 |
| 第三方工具调研 | 起点图、OpenClaw、fanqie_auto_publish 等社区工具 |
| Web 搜索 | 2024-2026 年公开信息，覆盖平台功能更新 |

### 1.4 关键假设（需验证）

| 假设编号 | 假设内容 | 验证状态 | 验证计划 |
|----------|----------|----------|----------|
| H1 | 番茄小说作家后台的数据可通过浏览器 DevTools 抓取 JSON 响应，无反爬对抗 | 未验证 | 在番茄作家后台打开 DevTools Network 面板，捕获数据统计页面的 API 请求 |
| H2 | 七猫作家助手的数据接口与网页版共享同一套后端 API | 未验证 | 抓包对比七猫作家助手 App 和网页版的 API 端点 |
| H3 | 晋江文学城作者后台无任何数据导出功能 | 已部分验证 | 需联系至少 1 位晋江签约作者确认后台实际功能（晋江作者后台为非公开页面，无法直接调研） |
| H4 | 阅文作家助手 App 的统计分析数据来自内部 API，可被 MITM 抓包获取 | 未验证 | 需在 Android/iOS 设备上对作家助手 App 进行 HTTPS 代理抓包 |
| H5 | 作者手动输入数据的错误率约 3-5%（数据录入领域通用基准） | 未验证 | 可在 test-novel-project 中进行 2 周手动输入试点，记录错误次数 |

## 2. 四平台数据获取能力对比

### 2.1 番茄小说（字节跳动）

#### 2.1.1 作家后台概况

- **入口**: fanqienovel.com/main/writer (网页版)
- **功能模块（8 个）**: 工作台、作品管理、数据统计、收益分析、互动管理、头条推荐、作者成长、账号设置
- **数据指标**（来源：番茄官方公告 + 知乎作者实际使用分享）:

| 数据类别 | 具体指标 | 粒度 | 延迟 |
|----------|----------|------|------|
| 核心数据 | 阅读人数（日/累计）、新增书架（日/累计） | 日级 | T+1（约12h） |
| 质量分析 | 章节读完率、章节跟读率、字数完读率（10万/20万/30万/50万）、追读率 | 日级 | T+1 |
| 收益分析 | 广告收益（日/月/累计）、礼物收益、活动奖金 | 日级 | T+1 |
| 流量来源 | 推荐来源分布、书架来源、搜索来源 | 日级 | T+1 |
| 读者画像 | 年龄分布、性别比例、地域分布、阅读时段 | 日级 | T+1 |

#### 2.1.2 数据获取/导出能力

| 能力 | 状态 | 详情 |
|------|------|------|
| 网页端数据查看 | **可用** | 数据统计页面含全部核心指标，图表可交互（7日/30日/自定义范围） |
| CSV/Excel 导出 | **不可用** | 经调研确认，番茄作家后台无任何数据导出按钮或下载功能 |
| 公开 API | **不可用** | 番茄小说未提供面向作者的开放 API |
| 字节跳动开放平台 | **不适用** | 字节开放平台面向小程序/小游戏开发者，与网文作者无关 |
| 浏览器抓包可行性 | **可能可行** | 数据统计页面的图表数据很可能通过内部 JSON API 加载；需实际抓包验证（见 H1） |
| 第三方工具 | **部分可用** | fanqie_auto_publish（GitHub）实现了自动发布和状态管理，但侧重章节发布而非数据提取；OpenClaw 技能可操作作者后台 |

#### 2.1.3 自动化可行性评估

番茄小说是四个平台中**自动化潜力最高**的平台:
- 数据指标最丰富（远超其他三个平台）
- 网页端功能完善，渲染方式现代（React/Vue SPA），内部 JSON API 可被捕获
- 社区已存在基于 Playwright 的自动化工具（fanqie_auto_publish），证明网页自动化技术可行
- 但需注意：字节跳动可能对批量请求有风控机制（参考其治理"刷量行为"公告）

#### 2.2.3 阅文开放平台 (open.yuewen.com)

**关键发现**: 阅文开放平台的 API 是 **B2B 内容分发 API**，不是作者数据 API。

| 维度 | 详情 |
|------|------|
| 平台定位 | 面向合作伙伴（阅读 App、有声平台等）提供文学内容接入 |
| 接入条件 | 需联系商务、签合同、产品联调（完整 B2B 入驻流程） |
| API 能力 | 书籍元数据查询、章节列表/内容获取、分类/标签查询、订单回传、阅读时长回传 |
| **作者数据** | **不提供**——API 返回的是面向读者的内容数据，不含收藏/订阅/追读/完读率等作者运营指标 |
| 适用对象 | 小米多看阅读、京东读书、懒人听书等第三方阅读平台，**不是**个体作者 |
| 结算数据 API | 存在"机构合作数据 API"，但仅面向签约合作方（出版社、渠道），不面向个体作者 |

**结论**: 阅文开放平台无法用于个体作者的数据自动化获取。这是一个 B2B 内容分销基础设施，不是 B2C 作者数据分析工具。

#### 2.2.4 数据获取/导出能力总结

| 能力 | 状态 | 详情 |
|------|------|------|
| 作家助手 App 数据查看 | **可用** | 可视化统计分析，含图表和趋势 |
| 作家助手桌面端/Web 数据查看 | **可用** | 网页端数据面板 |
| CSV/Excel 导出 | **不可用** | 经调研确认无导出功能 |
| 面向作者的开放 API | **不可用** | 阅文开放平台为 B2B 内容分发 API，不含作者侧数据 |
| App HTTPS 抓包 | **可能可行** | 作家助手 App 的数据很可来自内部 API；需 MITM 代理抓包验证（见 H4） |
| 第三方数据工具 | **部分可用** | 起点图（qidiantu.com）提供起点书籍的首订追踪、推荐位监控、徽章发放记录等**公开数据**聚合；但不提供个体作者需要登录才能看到的私有运营数据 |

### 2.4 晋江文学城

#### 2.4.1 作者后台概况

晋江文学城是四个平台中**数据工具最原始**的平台:

- **后台定位**: 以内容管理（发文、修文、章节管理）和收益记录为主，对运营数据分析的重视程度远低于番茄和起点
- **作者可见的数据**:
  - 积分（根据点击、收藏、评论等综合计算）
  - 收藏数
  - 评论数
  - VIP 章节收益记录
  - 霸王票（打赏）记录
  - 营养液（读者赠送的免费道具）
- **没有**完读率、追读率、章节留存率等精细化数据指标
- **没有**流量来源分析、读者画像分析
- 公开排行榜（积分榜、字数榜、收入金榜等）可查但仅限前排名次

#### 2.4.2 数据获取/导出能力

| 能力 | 状态 | 详情 |
|------|------|------|
| 网页端数据查看 | **基础可用** | 数据指标有限，界面传统（非 SPA） |
| CSV/Excel 导出 | **不可用** | 经调研确认无导出功能 |
| 公开 API | **不可用** | 晋江无任何形式的数据 API |
| 网页抓取/爬虫 | **受限** | 晋江有较强的反爬机制；社区工具 novel-downloader 通过 Token 认证后可获取内容，但获取的是阅读内容而非作者数据 |
| 作者后台自动化 | **难度极高** | 晋江后台为传统服务端渲染页面（非 SPA），且页面结构较复杂，自动化脚本维护成本高 |

#### 2.4.3 自动化可行性评估

晋江是四个平台中**自动化潜力最低**的平台:
- 缺少完读率、追读率等关键数据，即使自动采集也无法获得番茄/起点级别的洞察
- 后台技术栈老旧（传统 SSR 页面），不适合现代 Web 自动化
- 反爬机制较强
- **建议策略**: 晋江平台放弃自动化采集；改为在数据监控 SKILL 中为晋江作者提供简化版手动输入模板（仅需输入积分、收藏、评论、收益 4 项核心指标）

### 2.5 四平台对比矩阵

| 维度 | 番茄小说 | 起点/阅文系 | 七猫小说 | 晋江文学城 |
|------|---------|------------|---------|-----------|

## 3. 三种接入方案对比

### 3.1 方案 A: 完全手动输入（现状）

**描述**: 作者登录各平台后台，逐项查看数据后手动填入数据监控模板。

| 维度 | 考评 |
|------|------|
| 作者操作步骤 | 每天: 登录 2-4 个平台 → 进入数据页面 → 查看 6-15 项指标 → 手打填入模板 → 每周汇总 1 次 |
| 单次耗时 | 约 8-15 分钟/天（取决于平台数量和指标数量） |
| 周耗时 | 约 60-105 分钟（含每周汇总） |
| 年耗时 | 约 52-91 小时 |
| 数据延迟 | 手动输入通常晚于数据更新时间 2-24 小时（取决于作者何时登录） |
| 错误率 | 数据录入领域基准约 3-5%（打字错误、看错行列、单位误解等） |
| 数据粒度 | 仅能记录作者手动看到的指标（通常只记核心 5-8 项） |
| 实现成本 | 零开发成本（SKILL 已存在手动输入模板） |
| 作者体验 | 差——重复性手工劳动，创作时间被挤压 |

### 3.2 方案 B: CSV 导入（中间方案）

**描述**: 作者从平台后台截图/复制数据到 CSV 模板文件，再由数据监控 SKILL 自动解析和导入。

| 维度 | 考评 |
|------|------|
| 作者操作步骤 | 每天: 打开 CSV 模板 → 填入当天数据（可批量粘贴） → 保存 → SKILL 自动导入 |
| 单次耗时 | 约 3-6 分钟/天（减少 50-60%） |
| 周耗时 | 约 25-45 分钟 |
| 年耗时 | 约 22-39 小时（节省约 30-52 小时/年） |
| 数据延迟 | 与手动输入相同 |
| 错误率 | 可降至 1-3%（自动验证 + 结构化模板减少错误） |
| 数据粒度 | 同手动输入 |
| 实现成本 | **中**——需要开发 CSV 解析器、验证引擎、错误处理流程（预估 2-4 人天） |
| 适用场景 | 所有四平台通用（平台无关的中间格式） |

### 3.3 方案 C: API/自动化接入（目标方案）

**描述**: 通过网页自动化（Playwright）+ 内部 API 抓包，自动从平台获取数据。

按平台可行性分阶段:

#### 3.3.1 番茄小说（第一阶段）

| 维度 | 考评 |
|------|------|
| 实现方式 | Playwright 或 Chrome DevTools Protocol 操作番茄作家后台 → 捕获内部 JSON API → 每日定时触发采集 |
| 可获取的数据 | 全部核心指标（阅读人数、完读率、追读率、收益、读者画像等 10+ 项） |
| 数据粒度 | 日级（可提升至小时级，取决于番茄后端 API 的更新频率） |
| 数据延迟 | T+0 ~ T+1（取决于采集时机，可接近实时） |
| 实现成本 | **高**——需要开发和维护反反爬策略（预估 5-8 人天） |
| 维护成本 | **持续**——番茄前端页面结构变更时需更新选择器 |
| 风险 | 账号风控（可能被判定为异常访问，需模拟人类行为模式） |

#### 3.3.2 起点/阅文系（第二阶段）

| 维度 | 考评 |
|------|------|
| 实现方式 | 作家助手 App HTTPS 抓包（MITM 代理）→ 分析 API 端点 → 在本地模拟请求获取数据 |
| 可获取的数据 | 收藏、订阅、月票、追读、收益等（具体取决于 API 返回的字段） |
| 数据粒度 | 日级（取决于阅文后端 API） |
| 实现成本 | **高**——App 抓包比 Web 自动化更复杂，且 API 无公开文档（预估 8-12 人天） |
| 关键风险 | 阅文可能对 API 请求有签名/加密机制；违反 ToS 风险较高 |

#### 3.3.3 七猫小说（第三阶段）

| 维度 | 考评 |
|------|------|
| 实现方式 | 类似番茄的网页自动化方案 |
| 实现成本 | 中等（5-8 人天） |
| 关键风险 | 七猫网页端数据功能仍在迭代中，API 可能不稳定 |

#### 3.3.4 晋江文学城

**不推荐自动化**。理由: 数据指标有限（无完读率/追读率），技术栈老旧不适合自动化，反爬机制强。建议晋江作者始终使用方案 A 或 B。

### 3.4 三种方案对比汇总

| 维度 | 方案 A: 完全手动 | 方案 B: CSV 导入 | 方案 C: API 自动化 |
|------|:---:|:---:|:---:|
| 年时间成本（作者） | 52-91 小时 | 22-39 小时 | < 5 小时 |
| 数据错误率 | 3-5% | 1-3% | < 1% |
| 数据延迟 | +2~24h | +2~24h | +0~1h |
| 数据粒度 | 5-8 项 | 5-8 项（受模板限制） | 全部可用指标（10+ 项） |
| 开发成本 | 0 人天 | 2-4 人天 | 20-30 人天（跨 4 平台） |
| 持续维护成本 | 0 | 低（Schema 偶尔更新） | 中高（对抗平台变更） |
| 作者体验评级 | 差 | 中 | 优 |
| 番茄适用性 | 可用 | 可用 | **推荐** |
| 起点/阅文适用性 | 可用 | 可用 | 可尝试（风险高） |
| 七猫适用性 | 可用 | 可用 | 可尝试 |
| 晋江适用性 | **推荐** | 可用 | 不推荐 |

## 4. 增量价值分析（B2 修正：量化对比）

### 4.1 时间成本量化

**假设基准**: 一个同时在番茄 + 起点发布的作者，每天需监控 10 项核心指标:

| 方案 | 单日耗时 | 周耗时 | 月耗时 | 年耗时 | 等效创作字数（按 2000 字/小时） |
|------|---------|--------|--------|--------|-------------------------------|
| A: 完全手动 | 12 分钟 | 84 分钟 | 6.1 小时 | 73 小时 | 约 146,000 字 |
| B: CSV 导入 | 5 分钟 | 35 分钟 | 2.5 小时 | 30 小时 | 约 60,000 字 |
| C: API 自动化 | 1 分钟（审核+触发） | 5 分钟 | 0.4 小时 | 4.5 小时 | 约 9,000 字 |

**节省的创作时间（相对于方案 A）**:
- 方案 B: 每年节省约 43 小时 ≈ 86,000 字（约 2 个月的日更章节量）
- 方案 C: 每年节省约 68.5 小时 ≈ 137,000 字（约 3.4 个月的日更章节量）

### 4.2 数据延迟对优化响应速度的影响

网文运营中，数据响应速度直接影响内容调整的及时性:

| 场景 | 手动输入（延迟 2-24h） | 自动化（延迟 < 1h） | 影响 |
|------|----------------------|---------------------|------|
| 首秀数据监控 | 作者可能在第 2 天才发现首秀数据 | 首秀启动后 1 小时内可知 | 早 23 小时调整推荐策略 |
| 章节流失定位 | 发布新章节后 1-2 天才发现读完率暴跌 | 发布后 2-4 小时可发现 | 提前 20+ 小时修正内容或调整更新节奏 |
| 追读下降预警 | 连续 3 天数据滞后，实际可能已下降 4-5 天 | 当天即可发现 | 提前 4 天识别读者流失趋势 |
| 推荐位效果评估 | 推荐上架 2 天后才确认效果 | 推荐当天即可评估 | 更早利用推荐窗口期 |

**量化影响**: 在番茄小说平台，首秀期的前 72 小时是流量分配关键窗口。如果数据延迟 24 小时，作者将失去 1/3 的优化窗口。对于日均收益 200 元的腰部作者，这 24 小时的优化窗口可能带来 50-200 元的收益差距。

### 4.3 错误率降低的量化收益

| 方案 | 输入错误率 | 10 项指标日均错误数 | 月影响 |
|------|-----------|-------------------|--------|
| A: 完全手动 | 3-5% | 0.3-0.5 项/天 | 9-15 项错误数据点/月 |
| B: CSV 导入 | 1-3% | 0.1-0.3 项/天 | 3-9 项错误数据点/月 |
| C: API 自动化 | < 1% | < 0.1 项/天 | < 3 项错误数据点/月 |

错误的金钱影响: 错误数据可能导致错误的优化决策（如误判某章为"高流失"而进行不必要的修改）。在网文领域，一次不必要的内容修改（重写 3000 字 + 读者流失风险）的成本估计在 200-500 元。

### 4.4 数据粒度提升的额外价值

方案 C（API 自动化）可以获取到手动输入无法覆盖的数据:
- **章节级读完率逐日趋势**: 手动输入通常只记录每周快照；自动化可每日追踪每个章节的变化，精确定位读者何时开始流失
- **读者画像变化**: 番茄提供年龄/性别/地域/阅读时段分布，这些数据手动输入成本极高（通常被省略），但自动化可以轻松获取
- **收益成分分析**: 广告收益 vs 礼物收益 vs 活动奖金的日级拆分

这些额外数据维度能带来更精准的内容策略。以读者画像为例: 如果发现核心读者从"18-23 岁男性"变为"30-40 岁女性"，内容风格调整可能带来 20-50% 的留存率提升。

### 4.5 ROI 总结

| 方案 | 一次性开发成本 | 年维护成本 | 年节省（作者侧） | ROI（1 年） |
|------|:---:|:---:|:---:|:---:|
| B: CSV 导入 | 2-4 人天 | 0.5-1 人天 | 30 小时/作者 | 中 |
| C: 番茄自动化 | 5-8 人天 | 2-4 人天 | 60+ 小时/作者 | 高 |
| C: 番茄+阅文+七猫 | 20-30 人天 | 6-12 人天 | 60+ 小时/作者 | 中高 |

> ROI 计算面向插件用户（作者）的体验提升，而非插件开发团队的金钱回报。如果插件为付费产品，方案 C 的自动化数据接入将成为**核心付费卖点**——"自动从番茄/起点抓取数据，告别手动记录"——这在目前网文工具市场几乎是空白。

```
CSV 文件导入
    │
    ▼
┌──────────────────────────────┐
│ 阶段 1: 格式预检             │
│ - 文件编码检测               │
│ - 必填字段检查               │
│ - 数据类型检查               │
└──────────┬───────────────────┘
           │
     ┌─────┴─────┐
     │ 通过?     │
     └─────┬─────┘
      N    │    Y
      │    │    │
      ▼    │    ▼
  ┌──────────┐  ┌──────────────────────────────┐
  │ 阻断      │  │ 阶段 2: 逐行数值验证         │
  │ 返回完整  │  │ - 范围检查                   │
  │ 错误列表  │  │ - 逻辑检查                   │
  │ 作者修正  │  └──────────┬───────────────────┘
  │ 后重新导入│             │
  └──────────┘       ┌─────┴─────┐
                     │ 存在 ERROR?│
                     └─────┬─────┘
                      Y    │    N
                      │    │    │
                      ▼    │    ▼
                  ┌──────────────┐  ┌──────────────────────────────┐
                  │ 按行返回错误  │  │ 阶段 3: 跨字段一致性验证     │
                  │ 明细          │  │ - 跨字段逻辑检查             │
                  │              │  │ - 趋势异常检测               │
                  │ 选项:        │  └──────────┬───────────────────┘
                  │ 1. 报告全量   │             │
                  │    错误，     │       ┌─────┴─────┐
                  │    由作者修正 │       │ 存在 WARNING?│
                  │    CSV 后重新 │       └─────┬─────┘
                  │    导入       │        Y    │    N
                  │ 2. 自动跳过   │        │    │    │
                  │    错误行，   │        ▼    │    ▼
                  │    导入其余   │  ┌──────────────┐  ┌──────────────┐
                  │    数据       │  │ 展示警告清单  │  │ 全部通过      │
                  │              │  │ + 建议修正    │  │ → 写入数据    │
                  │ (不推荐自动   │  │              │  │   存储        │
                  │  跳过——       │  │ 作者确认:    │  └──────────────┘
                  │  部分数据可能 │  │ 1. 忽略继续  │
                  │  导致分析偏差)│  │ 2. 修正后重导│
                  └──────────────┘  └──────────────┘
```

**设计原则**:
- ERROR 级别: 硬阻断——数据明确违反格式或取值范围，不导入
- WARNING 级别: 软提示——数据可能异常但仍可导入，提示作者确认
- INFO 级别: 信息提示——不影响导入，仅作为改进建议
- **不用部分成功/部分回滚**——为了避免不完整数据集导致的错误分析，当存在 ERROR 时默认阻断全部导入，要求作者修正后重新导入
- **提供"忽略 ERROR 强制导入"选项**——供作者在确认数据无误（如平台显示的特殊情况）时使用，但有明确的风险提示

## 6. 推荐实施路径

### 6.1 分阶段实施计划

#### 阶段 0: 立即可做（0-1 周）

- [ ] 在数据监控 SKILL 中优化手动输入模板，增加数据校验（减少手动输入错误）
- [ ] 为晋江作者创建简化版数据输入模板（仅 4 项核心指标）
- [ ] 编写"数据采集最佳实践"指南（含截图标注各平台数据位置）

#### 阶段 1: CSV 导入方案（1-3 周）

- [ ] 开发 CSV 解析器和验证引擎（按本报告 5.2-5.4 设计）
- [ ] 创建各平台的 CSV 导入模板（含表头预填和自动格式化）
- [ ] 实现"CSV 导入 → 自动填充周报"的完整流程
- [ ] 在 test-novel-project 上进行多平台多场景测试

#### 阶段 2: 番茄小说自动化采集（3-6 周）

- [ ] **验证 H1**: 在番茄作家后台进行 DevTools 抓包，确认内部 API 端点
- [ ] 开发 Playwright 自动化采集脚本
- [ ] 实现每日定时采集 + 数据自动写入
- [ ] 添加反风控策略（随机延迟、人类行为模拟）
- [ ] 灰度发布：邀请 5-10 位番茄作者内测

#### 阶段 3: 起点/阅文自动化采集（6-10 周）——条件触发

- [ ] **前置条件**: 阶段 1+2 已完成且用户反馈积极
- [ ] **验证 H4**: 对作家助手 App 进行 HTTPS 抓包分析
- [ ] 评估 API 可复制性（签名/加密/Token 机制）
- [ ] 如果 API 可复制: 开发自动化采集脚本
- [ ] 如果 API 不可复制: 降级为网页自动化方案

#### 阶段 4: 七猫自动化采集（8-12 周）——低优先级

- [ ] **前置条件**: 验证七猫作者的数据需求足够大（通过阶段 1 的 CSV 导入数据统计）
- [ ] 七猫自动化实现

**晋江**: 不进入自动化路线图。始终使用优化后的手动输入或 CSV 导入。

### 6.2 开发优先级矩阵

```
                    影响力
            高                 低
        ┌─────────────┬─────────────┐

  低    │ 阶段2: 番茄 │ 阶段4: 七猫 │

```

推荐顺序: 阶段 1 → 阶段 2 → 阶段 3 → 阶段 4

### 6.3 风险与应对

| 风险 | 概率 | 影响 | 应对 |
|------|------|------|------|
| 番茄/阅文检测到自动化访问并封禁账号 | 中 | 高 | 检测频率控制（每日 1-2 次）；模拟人类行为；准备手动降级方案 |
| 平台数据结构变更导致采集失败 | 高 | 中 | 自动化脚本含健康检查（采集失败时通知作者手动输入）；版本特征检测 |
| 平台推出官方 API/data export 功能 | 低 | 正 | 持续关注平台更新公告；官方 API 上线后废弃反向工程方案 |
| 自动化采集违反平台 ToS 法律风险 | 低 | 高 | 仅采集作者自己有权查看的数据；不共享/出售数据；仅用于个人分析 |
| CSV 导入的格式维护负担 | 中 | 低 | Schema 版本化；向后兼容旧格式；提供自动格式迁移工具 |

## 核心数据
